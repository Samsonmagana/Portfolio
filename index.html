    How I work

    A repeatable process keeps quality high and surprises low.

    1. Understand the problem

      I start with who will use the software and what they need to achieve, then confirm it before writing code.

    2. Design the data and the screens

      Tables, relationships and page layouts are sketched first, so the code has a clear shape.

    3. Build in small, working steps

      One feature runs end to end before the next begins, which keeps progress visible and bugs small.

    4. Test, then fix the cause

      I try to break what I build, read the error carefully and correct the root cause instead of the symptom.

    5. Document for the next person

      A clear README and readable code mean a teammate can pick up my work without a handover meeting.
